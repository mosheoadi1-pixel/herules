## Browser suite: "Release my pause" wait (line 182) - 2026-11-15

Root cause: the wait after the 503 `/api/state` route is removed used a 12-second budget. The client recovers only through its own refresh: `src/main.tsx` line 49 polls every 5 seconds, and `src/api.ts` line 2 aborts any read after 15 seconds. A read that hangs for its full 15 seconds, followed by the next 5-second poll, can take up to about 20 seconds, so 12 seconds is shorter than the app's own recovery bound. The product code is not wrong: the pause button is rendered from `s.pauses.includes(u.id)` in `src/main.tsx` line 177, which becomes true on the first successful read. Owner-only release is enforced by the server (`server/app.ts`, the `pause` and `resume` branches), and the test asserts nothing about it.

Evidence: the working tree failed at line 182 with `locator.waitFor: Timeout 12000ms exceeded` for `getByRole('button', { name: 'Release my pause', exact: true })`. A HEAD baseline with the current test failed at the same line once in five runs. Diagnostics on that baseline showed the button visible within about 0.5 seconds in the runs that passed, with a successful state read right after the route was removed, so the failure is an intermittent slow read rather than a missing control. The failing run was not captured with full logs; the hung-read path is the likely cause, not directly observed. HEAD's committed `tests/browser.ts` fails earlier, at line 78 (the closed check-in panel), so it cannot serve as a baseline on its own.

Fix: `tests/browser.ts` line 182 now waits up to 25 seconds, with a comment explaining the bound. Product code is unchanged.

Verification: `npm.cmd run test:browser` passed twice in a row; `npm.cmd test` passed; `npm.cmd run build` passed.
