# Paired gameplay: branch inventory and verification

`src/GameApp.tsx` (the gameplay previously mounted by `src/main.tsx`) and its mounted components are the UI inventory. `server/app.ts` is the HTTP and engine inventory; the older room/session protocol is in `server/public-sessions.ts` and `server/public-play.ts`. This is not an inventory of the legacy demo.

| Feature in the branch | Paired implementation and evidence |
| --- | --- |
| Private role login, automatic singleton pairing/reopening, guest/register/login, reset/reseed | Intentionally excluded. Public uses separately verified accounts and an accepted invitation. One invitation ID identifies one game; a new invitation creates a new game, even for the same people. The paired requests do not claim private singleton roles or create private users. |
| Time and safety | Private supports unlimited or timed sessions and `extend` at API level; `approve`/`revise` are compatibility no-ops. Paired has separate affirmative opt-ins, shared revisioned terms and optional duration, independent holds, permanent stop, withdrawal, and consent-checked time changes (no unilateral extension). Agreed invitation date is plan metadata, not a start gate. Close/cancel archive the game, and blocks hide it from both sides. API suite covers independent holds, revision gates, cancellation, block and archive; browser exercises opt-in, hold/resume and stop. |

## Storage and compatibility

- Existing plans and invitation IDs retain their old lifecycle; migration 014 adds new tables without altering old rows. The engine lazily maps the prior mission history when an older session first opens the expanded game. The original earned awards remain in the legacy ledger; the session starts with a spendable balance derived from those awards. A new approval writes only the new ledger, under the same transaction as the session aggregate.
- Roles are derived from verified conversation membership, not the participant’s gender or a request field. The adapter maps `dom`/`sub` to the legacy engine’s internal role names only. New paired actions are scoped to the invitation, revalidated server-side, and recorded against the actor’s idempotency key and input. The room advisory lock precedes the authorization and session row locks, including for lazy migration. Block and conversation close serialize against gameplay. Read projections redact private game data before building the digest.
- The original play endpoint is retained for legacy history and committed retries, and either participant can still stop via a cached client. Fresh legacy mutations cannot create, advance or award a mission, including on older invitations. All active play uses the new consent gate.

## UI review scope

Used `ui-ux-pro-max` guidance on navigation/back, feedback states, heading hierarchy, WCAG focus visibility, and reduced motion. The paired view shows the partner, role, and session status before controls; offers a clear consent or draft action; groups secondary destinations under “More in this session”; explains lifetime versus spendable points; and keeps safety controls independent of ordinary busy state. Browser history returns to the inbox or original conversation without losing the unsent conversation draft. Loading and retry are explicit, and blocked content is cleared rather than left on the screen.

The Chromium suite covers launch from the accepted invitation, reentry from the inbox, browser back/forward, keyboard and restored focus, mixed-direction title, Hebrew and English, desktop and 375px, a temporary fetch failure, mission approval/return, paused/terminal states, and blocking. This is representative coverage, not a full walkthrough of every tool, every device, or a screen-reader audit.
